# 履歴量による負荷の測定

`npm ci`の後、`npm run bench`でVitest内蔵のベンチマークを実行します。追加の依存は不要です。通常の`npm test`とCIからは分離し、実行速度の合格閾値は設けません。

## 条件

`benchmarks/scaling.bench.ts`で100・500・1,000コミットの状態を作成します。各コミットは約1KiBの内容を持つ5ファイルを保持し、4コミットごとに分岐とマージを含めます。同時刻コミットと11・51・101本のローカルブランチ、10・50・100組のupstream参照を作成します。設定・利用者の実データ・実GitHub接続は使用しません。

次の4操作を、fixture生成時間を除いて測ります。

- `layout`: `calculateGraphLayout`のノード・リンク配置
- `snapshot`: `GitEngine.getState`のstateコピー
- `status`: `GitEngine.execute('git status')`の解析・stateコピー・出力生成・状態比較
- `tracking`: `trackingStatus`のahead/behind計算

計測前にノード/リンク数・upstream数とstatus成功を確認し、計測後にはengineのstateが変わっていないことを確認します。各操作は100ms・最低3回のウォームアップ後、500ms・最低30回を測定します。処理が遅い環境では指定時間を超えて最低回数まで実行します。

## レポート

端末には平均時間（ms）とサンプル数、`benchmark-results/scaling.json`には平均・p99・サンプル数・相対誤差幅と条件を保存します。測定時刻、GitのHEAD、未コミット変更の有無、Node/Vitest、OS/CPU、fixtureと計測設定も記録します。Git/ESLintの対象外で、再実行時に上書きされます。

他の重い処理を止め、同一環境・同一fixtureと設定で比較してください。サンプル数や誤差幅を併記し、単発のp99を性能保証や回帰の断定に使いません。未コミット変更がある場合、HEADだけでは計測対象を再現できないため、その差分も保存してください。

これはNode上の計算負荷です。React/SVGの描画、端末ログのDOM増加、スクロール、スマホCPUやブラウザメモリ、長時間利用時の状態蓄積は測定しません。O01/O02の計測の一部を追加するもので、O03の履歴上限や仮想化の導入を決める根拠として単独では扱いません。

## 導入時の測定例（2026-10-25）

main`5f6dd12`に本計測コードを追加した未コミット状態で、Node.js22.20.0・Vitest5.0.5・macOS/arm64・Apple M1 Proで実行しました。平均時間の単位はmsです。

| コミット数 | layout | snapshot | status | tracking |
| ---: | ---: | ---: | ---: | ---: |
| 100 | 0.060 | 1.087 | 1.950 | 0.071 |
| 500 | 0.795 | 5.093 | 8.754 | 2.063 |
| 1,000 | 2.957 | 10.555 | 17.643 | 9.367 |

各測定は30〜8,348サンプルです。履歴量とブランチ数を同時に増やした合成条件で、通常教材の遅さを示す値ではありません。1,000コミット時はstateコピーとstatusの時間が目立ちますが、この結果だけでエンジン分割やブラウザ描画の最適化を行いません。実利用に近い条件で次の計測対象を選ぶための初期値として残します。
