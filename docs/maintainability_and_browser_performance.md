# 保守性と長時間利用の性能を併せて改善する方針

2026-10-26 JSTの相談で、E08（機能ごとの責務分割）とO03（長いログ・一覧の性能）の両方を詰めていく方針を合意しました。本書は実施方針と完了条件の記録です。追加のブラウザ計測・責務分割・性能改善はまだ実施していません。

## 目的と現在の状態

機能追加や修正の影響を限定できる構造と、長時間使っても操作しやすい性能を両立します。分割の前後を同じ条件で測定し、効果と回帰を確認します。

- [GitEngine](../src/engine/git-simulator.ts)にはファイル・履歴・remote等の処理が残っています。[状態の共通処理](../src/engine/git-state.ts)・高度な操作・模擬GitHub等は既に分離されており、全体の作り直しを前提にしません。
- [学習画面](../src/app/game/page.tsx)は端末出力と入力履歴を追加し続け、[端末表示](../src/components/terminal-output.tsx)は受け取った出力を描画します。通常利用での性能障害を実測したという記録ではありません。
- [既存の性能計測](performance_baseline.md)はNode上の履歴量に対する計算負荷です。ブラウザ描画・長時間利用・端末メモリの根拠として単独では使いません。

O01/O02の未完了部分に当たるブラウザ計測も同じ調査に含め、重複した計測基盤を増やさないようにします。実画面・実端末の確認は従来の依頼どおり対象外です。自動ブラウザの結果と実機の結果を区別します。

## 実施順

### 1. 現在の性能を測り、比較基準を作る

ログ量、操作回数、コミット数、ファイル量を別々に増やし、どの条件が負荷につながるか確認します。ログ量の候補は100・1,000・5,000行とし、長い一行も別に扱います。既存の合成履歴も利用し、生成時間と測定対象の処理時間を分けます。

入力から表示までの応答、ログ追記・スクロール・描画時間、DOM要素数、利用可能な環境でのメモリ、Git状態のコピー時間を測ります。メモリ等を測定できない環境では未測定と明記します。

ブラウザ・画面寸法・実行環境・対象コミット・fixture・反復回数を記録し、ウォームアップと複数回測定でばらつきを確認します。改善前後は同じ条件で比較します。初期計測を基に対象操作と性能目標を具体化し、改善に入る前に比較条件を固定します。

### 2. 調査した処理から、責務を一つずつ整理する

変更が集中する箇所や負荷のある処理を調べ、最初の分割対象を選びます。remote操作等は候補ですが、今回の相談だけで対象を固定しません。

呼び出す側が内部の状態管理を知らずに使える、小さなinterfaceを持つmoduleへまとめます。公開メソッドの使い方を維持し、内部の処理順序や多数の細かな操作を呼び出し側へ押し付けないようにします。ファイルを増やすこと自体を完了条件にしません。

コマンドの成功・拒否、失敗時の状態保持、採点、履歴、保存・再開を既存のinterfaceから検証します。責務分割と性能改善を別の変更として扱い、分割段階でも同じ性能条件で回帰を確認します。

### 3. 負荷が確認できた箇所を改善する

実測結果に応じて、表示範囲の仮想化、再計算やコピーの削減等を比較し、必要な対策を選びます。十分な問題が確認できなければ、追加の最適化を見送り、その判断根拠を残します。

ログの表示範囲を絞る方法と、古い内容を保持しない方法は影響が異なります。保持上限や自動削除を採用する場合は、対象・保持範囲・利用者への説明と、コピー・履歴検索・checkpoint・バックアップへの影響を先に仕様化します。計測前にログ削除を決め打ちしません。

過去ログ閲覧中のスクロール位置、新しい出力への追従、キーボード操作・フォーカス、出力コピー、保存・再開を含めて確認し、改善前後の効果と副作用を報告します。

## 完了条件とステータス

| 段階 | 完了条件 |
| --- | --- |
| 計測 | 再現可能な条件・測定結果・未測定項目を記録し、分割/改善の対象と優先順位、または対策を見送る根拠を示せる |
| 責務分割 | 対象処理の変更が局所化し、呼び出し側の使い方と既存動作を維持できる。回帰テストと性能比較で影響を説明できる |
| 性能改善 | 選定した対策の前後を固定条件で比較し、効果・ばらつき・利用者への影響を説明できる。コピー・検索・保存等の仕様と挙動が一致する |

全体の判断軸は「変更の影響を限定できる」「既存動作が保たれる」「測定条件に対して性能を説明できる」の3つです。未着手の段階や未測定の範囲を、方針を記録しただけで完了にはしません。実装・検証・マージ後、対象範囲と関連PRをロードマップへ反映します。

## E04の扱い

E04（index表現の全面統一）は保留を維持し、E08/O03を進める前提条件にはしません。現在は共通のindexTreeで表現差を吸収しています。

調査で表現差に起因する不具合や、統一が必要な具体的な保守上の問題が見つかった場合は、その部分を検討します。保存形式を変更する必要がある場合は、既存checkpoint・stash・worktree・操作中の状態の互換性と移行・戻し方を別途設計します。

既存の調査履歴は[ロードマップ](remaining_work_roadmap.md)に残し、現在の進め方は本書と[最新の対応状況](lightweight_improvements.md)を優先します。
